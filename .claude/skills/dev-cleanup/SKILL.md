# Чистка dev-стенда и диска

Проект копит мусор в четырёх местах сразу, и каждое проявляется по-своему. Проверять все четыре —
чинить по одному бесполезно.

| Где | Симптом | Порядок величины (замер 21.08.2026) |
|---|---|---|
| dev-БД после e2e | тесты «плавают» без правок кода | 1900 задач, 7000 событий, 2000 станков |
| `.next` по ворктри | кончается место на ноутбуке | **9,4 ГБ** на 6 ворктри |
| Docker (локально) | то же | **17,5 ГБ** кэша сборки и старых образов |
| Docker (прод) | деплой падает по месту | **28 ГБ** кэша сборки, диск 77% |

## 0. Сначала замерить, потом удалять

Не чистить вслепую: цифры «до/после» — это и проверка, что чистили то самое, и материал для отчёта.

```bash
du -sh /Users/nonamenoname/Documents/vanmark-drive
```

```bash
docker system df
```

```bash
docker exec vanmark-postgres psql -U vanmark -d vanmark -t -A -F'|' -c "SELECT relname, n_live_tup FROM pg_stat_user_tables WHERE n_live_tup > 100 ORDER BY n_live_tup DESC LIMIT 10"
```

## 1. dev-БД: `pnpm db:clean:dev`

**Главный симптом, ради которого всё это затевалось.** e2e гоняются против ОДНОЙ общей dev-БД
(`e2e/reset.ts`, `playwright.config.ts` → `reuseExistingServer`), и каждый прогон оставляет задачи,
станки, события и вложения. На двух тысячах заявок список «Все задачи» весит ~2,5 МБ, клиент
рендерит полторы тысячи строк, и тесты вида «создали заявку → нашли её поиском» начинают падать
через раз. **Это не регрессия кода** — прежде чем расследовать такое падение, сверься с базой.

```bash
pnpm db:clean:dev
```

Скрипт (`prisma/clean-dev.ts`) сносит задачи, станки, смены, отсутствия и всю их обвязку, обнуляет
последовательности номеров и **сохраняет** пользователей, пароли, справочники типов и работ,
настройки KPI и ёмкости. Прод чистить им нельзя — он отказывается работать на нелокальном
`DATABASE_URL`.

⚠️ **Добавили таблицу, ссылающуюся на `Task` или `Machine` внешним ключом БЕЗ каскада — впишите её
в `clean-dev.ts` ДО удаления задач/станков.** Иначе очистка молча ломается об `ON DELETE RESTRICT`,
и обнаружится это через месяц, когда база снова разрастётся (ровно так случилось с `TaskMachine`
21.08.2026).

## 2. Осиротевшие загрузки

Скрипт чистит строки вложений, но до файлов не дотягивается: `UPLOADS_DIR` у каждого стенда свой.
После шага 1 всё содержимое каталога — сироты.

```bash
rm -rf data/uploads/*
```

В каждом ворктри свой каталог — пройти по всем.

## 3. Кэш сборки Next и артефакты Playwright

Самый жирный кусок на ноутбуке: `.next` разрастается до 1–3 ГБ **в каждом ворктри**, а ворктри
живут месяцами. Каталог полностью восстановимый — следующий `pnpm dev` его пересоберёт.

**Перед удалением убедиться, что dev-сервер не запущен** — снести `.next` под живым процессом
значит получить непонятные 500 на ровном месте:

```bash
pgrep -fl "next-server|next dev"
```

Пусто — можно удалять, в каждом ворктри и в основном каталоге репозитория:

```bash
rm -rf .next test-results playwright-report
```

Список ворктри: `git worktree list`.

## 4. Docker локально

```bash
docker builder prune -af
```

```bash
docker images --format '{{.Repository}}:{{.Tag}} {{.Size}} {{.CreatedSince}}'
```

Образы старше нескольких недель, не привязанные к запущенному контейнеру (например,
`vanmark-app:localtest`), удалять точечно по имени — `docker image prune -a` может снести нужное.
Postgres-образ **не трогать**: на нём стоит контейнер dev-БД.

## 5. Docker на проде — только `builder prune`, и НЕ всё подряд

Кэш сборки на VPS растёт быстрее всего: каждый деплой добавляет слои, старые никто не убирает.
Диск 48 ГБ, и при 77% занятости следующая сборка рискует не влезть.

Проверить:

```bash
ssh vanmark-prod 'df -h / | tail -1; docker system df'
```

Чистить **с фильтром по возрасту**, а не `-af`: свежие слои держат следующий деплой быстрым
(~1 минута вместо ~20 на холодную).

```bash
ssh vanmark-prod 'docker builder prune -f --filter until=24h'
```

После чистки — обязательно убедиться, что прод живой:

```bash
ssh vanmark-prod 'curl -fsS https://vmdrive24.ru/api/health'
```

**Запрещено на проде:** `docker system prune -a` (снесёт рабочие образы), `docker compose down -v`
(убьёт volume с базой и загрузками), любое удаление из `/backups` (там дампы, ротация уже настроена
cron'ом на 14 дней).

## 6. Что НЕ трогать

- **`node_modules`** — pnpm держит их хардлинками в общем сторе; `du` показывает объём по каждому
  ворктри, но реальное место одно. Удаление ничего не освобождает, а `pnpm install` стоит времени.
- **Backup-таблицы в БД** (`machine_category_backup_20260820`, `machine_number_backup_20260815`) —
  страховочные копии от миграций, переносивших данные. На проде это сеть безопасности, на dev — 1000
  строк, то есть ничто. Они всплывают в `prisma migrate diff` как «лишние» — это ожидаемо, не баг.
- **Прод-БД** — чистить нечем и незачем: 300 КБ дампа, это боевые данные (CLAUDE.md, правило 7).

## 7. Отчёт

Коротко: что было / что стало по каждому пункту, сколько освободилось, и — если чистили dev-БД —
предупреждение, что стенд теперь пустой (нужен `pnpm db:seed` или `db:seed:pilot`, если нужны
демо-данные).
