# Деплой и релизы

Прод: один VPS в РФ, Docker Compose (`app` + `postgres` + `caddy`), фото в volume `/data/uploads`. Деплой допустим в нерабочее время команды (до 08:00 / после 20:00 МСК) или по согласованию с Артёмом — кроме хотфиксов.

## Первичная настройка сервера (один раз)

1. VPS: Ubuntu LTS, 2 vCPU / 2–4 ГБ; ufw: открыты только 22/80/443; ssh-ключи, root-вход выключен; fail2ban.
2. Docker + compose; склонировать репозиторий; заполнить `.env` по `.env.example` (секреты сгенерировать: `openssl rand -base64 32`, VAPID — `npx web-push generate-vapid-keys`).
3. DNS A-запись → IP; Caddy получит TLS автоматически.
4. Cron-бэкапы (см. ниже) + проверить восстановление на чистом контейнере ДО запуска пилота.
5. Сид: пользователи (Милена, водители, Артём-админ), справочник типов задач, стартовый номер sequence (уточнить у Артёма последний номер из Telegram-чата).

## Каждый релиз — по порядку

1. Локально: `pnpm lint && pnpm typecheck && pnpm test && pnpm e2e` — зелёные; security-check пройден, если менялись API/БД.
2. На сервере перед обновлением — бэкап: `pg_dump` в файл с тегом релиза + снапшот uploads (если менялась логика файлов).
3. `git pull` → `docker compose build app` → `docker compose run --rm app pnpm prisma migrate deploy` → `docker compose up -d app`.
4. Healthcheck: `curl -f https://<домен>/api/health` (эндпоинт обязателен с этапа 1).
5. Версия SW: `curl -f https://<домен>/sw-version.js` — должна отдать `self.SW_VERSION = "b<временная метка>"` НОВОЙ сборки (не 404 и не прежнее значение). Если файл не сгенерился, SW молча остаётся на VERSION="dev": имя кэша перестаёт меняться, обновления клиентов и ротация кэша умирают без единого симптома.
6. Smoke на проде: вход диспетчером, открыть «Сегодня»; вход водителем с телефона, открыть «Мои задачи»; создать тестовую задачу и удалить.
7. Build-skew: если менялись `public/sw.js` / стратегия кэша — открыть вкладку СТАРОЙ сборки (оставленную с до-деплоя) и убедиться, что она дожила до перезагрузки без белого экрана (CLAUDE.md, конвенция про service worker).
8. Сообщить Артёму: версия, что вошло, что проверить руками.

## Если сервер недоступен со стороны Claude (частый случай)

IP Claude регулярно оказывается в бане fail2ban — тогда не проходят ни `ssh`, ни `curl` к домену
(`Connection refused` / код 000 при живом проде). Проверять ОДНИМ подключением и не долбиться серией
попыток: каждая новая попытка продлевает бан. Убедившись в блокировке — сразу выдать Артёму
инструкцию для KVM-консоли Timeweb, а не искать обходные пути.

Требования к такой инструкции (Артём не программист, копирует по одной команде):

- каждая команда — отдельным блоком ```bash, по одной команде в блоке, без `$` и без вывода внутри;
- порядок: `cd /opt/vanmark` → **бэкап** (`pg_dump` в `/backups/db-<дата>-<тег>.dump` + проверка `ls -lh`,
  что файл не пустой) → `git pull origin main` → сборка → миграция → `up -d app` → проверки;
- **сборку запускать фоном с логом, а НЕ в tmux**: серийная консоль Timeweb рисует tmux криво, и
  выглядит это как «консоль отвалилась».
  `nohup docker compose -f docker-compose.prod.yml build app > /tmp/build.log 2>&1 &`, следить
  `tail -f /tmp/build.log` (Ctrl+C прерывает только просмотр). Признак успеха — `Image vanmark-app Built`;
- миграцию гонять из НОВОГО образа одноразовым контейнером
  (`docker compose -f docker-compose.prod.yml run --rm app npx prisma migrate deploy`) ПОСЛЕ сборки, но
  ДО подъёма приложения: старый код переживает аддитивную миграцию, новый без неё падает;
- проверки после: `/api/health`, `/sw-version.js` (сверить с меткой из лога сборки), `ps`, плюс
  запрос к БД, подтверждающий суть релиза (например, что номера проставились);
- в конце — команда отката (`git checkout <прошлый коммит> && … up -d --build app`) и восстановление
  дампа, с пояснением, когда это реально нужно;
- сказать заранее, сколько ждать (прод-сборка ~20 мин) и что вкладку консоли можно закрыть.

## Сиды на проде — правила безопасности

- **Полный `pnpm db:seed` на проде запрещён**: он перетирает пароли всей команды по `SEED_PASSWORD`.
- Новых сотрудников и справочники заводим ТОЧЕЧНЫМИ сидами, которые не трогают существующие записи:
  `db:seed:roster` (подменный водитель, директор), `db:seed:service-manager` (менеджер-сервисник,
  логин/имя — `SM_LOGIN`/`SM_NAME`, пароль — `SEED_PASSWORD_MAXIM`), `db:seed:capacity` (параметры ёмкости).
- После сида проверить вход нового сотрудника и что он видит ТОЛЬКО свой раздел.

## Миграции — правила безопасности

- Только `prisma migrate deploy` на проде (никогда `migrate dev` / `db push`).
- Миграция, добавляющая значение в enum (`ALTER TYPE ... ADD VALUE`), идёт ОТДЕЛЬНЫМ файлом от
  миграции, которая это значение использует: Postgres не даёт применить оба в одной транзакции.
- Разрушающие миграции (удаление/переименование колонок с данными) — в два релиза: сначала совместимый код, потом удаление. Перед ними — обязательный бэкап и подтверждение Артёма.

## Бэкапы (cron на VPS)

```
0 3 * * * pg_dump -Fc > /backups/db-$(date +\%F).dump      # ежедневно
30 3 * * * tar czf /backups/uploads-$(date +\%F).tgz /data/uploads
0 4 * * * find /backups -mtime +14 -delete                  # ротация 14 дней
```

Плюс копия последнего бэкапа на внешнее хранилище (S3-совместимый бакет или второй сервер). Раз в месяц — тестовое восстановление.

## Откат

1. `git checkout <предыдущий тег>` → build → up.
2. Если миграция несовместима — восстановить дамп: `pg_restore --clean` из бэкапа шага 2 (потеря данных с момента бэкапа — сообщить Артёму, восстановить вручную из журнала, если критично).
3. Записать причину отката и починить в ветке, не на проде.

## Запрещено

- Деплой без бэкапа. Ручные правки кода/БД на сервере. `docker compose down -v` (убивает volumes). Секреты в логи/коммиты.
